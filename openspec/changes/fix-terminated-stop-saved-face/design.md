## Context

See proposal.md (Why). Current state: `StopTimerIntent` (plain `AppIntent`, widget extension process) saves via `LocalStore` (`createEntry` + `clearTimerDraft`, `source='manual'`) and posts the payload-less `LiveActivitySignal` Darwin notification; ending stays app-side because `Activity<T>.activities` enumerates empty in the extension (archived `2026-10-10-live-activities` D8, device-proven over two builds). With the app dead, the Darwin post is lost, the `BGAppRefreshTask` chain cannot fire after a user force-quit (OS policy) and is minutes-late after jetsam — so the banner/Island ticks the running face forever although the entry is saved. Faces branch on `context.state.savedDurationSeconds` (`TimerLiveActivityWidget`: banner, expanded regions, and `islandElapsed` all handle saved-vs-running), which only the app (or a push server) can set. Push tokens were an explicit non-goal; "Stop works without opening the app" is spec.

ctx7: `/websites/developer_apple_activitykit` — "AppIntent button in Live Activity updating activity UI", "LiveActivityIntent openAppWhenRun", "LiveActivityIntent protocol start update end Live Activity". Pin: iOS 18 SDK via Xcode 16+. Docs confirm update/end need an `Activity` instance and that `LiveActivityIntent` grants background `request()` — but say nothing about enumeration/update/end from the intent process, hence Spike A below.

## Goals / Non-Goals

Goals: with the app dead, a successful Island/banner Stop replaces the ticking running face with the existing `✓ Saved <duration>` face (same strings, same layout, true duration only); full dismissal still happens app-side on contact. Non-goals (design-level): no push tokens/APNs/relay work; no `openAppWhenRun` (app must not pop open on Stop); no new Saved visual language; no dismissal-timing change; no save-path/provenance change; no new entitlements, targets, or DB schema.

## Decisions

**D1 — Spike A first: `LiveActivityIntent` privilege probe (cheapest, may obsolete the rest).**
Conform `StopTimerIntent` to `LiveActivityIntent` (keeping the app closed — `openAppWhenRun = false`) and, on-device with the app terminated, log `Activity<TimerActivityAttributes>.activities.count` from inside `perform()`. Rationale: the D8 "always empty" finding was proven with a plain `AppIntent`, while Apple grants `LiveActivityIntent` background ActivityKit privileges — an untested combination. If non-empty, the intent calls `update()` (Saved face, no dismissal) or `end(saved, .after(6s))` directly and the sidecar path (D2–D4) is dropped. Alternative (assume D8 covers all intent kinds) rejected: one device run settles it, and success is the complete fix. If empty, proceed with D2–D4 unchanged.

OUTCOME (Spike A, 2026-10-10): empty — enumeration is STILL `0` in a `LiveActivityIntent` process with the app dead. D8 stands; proceeded to Spike B.

**D2–D4 — SUPERSEDED by Spike B (do not land).**
The run-keyed save sidecar (D2), face resolution (D3), and app-side reap cleanup (D4) below were fully implemented — then disproven on-device.

OUTCOME (Spike B, 2026-10-10, iPhone 17 simulator, full D2–D4 code live): NEGATIVE — face frozen. Terminated-app Island Stop saved `Island repro|80|manual`, cleared the draft, and wrote the sidecar — but AX still read "timer running, Stop and save timer" with Stop offered across minutes. Root cause: the `Text(timerInterval:)` tick does not re-evaluate the `ActivityConfiguration` body, so the sidecar is never read; no intent-process API can push new content (Spike A). The D2–D4 code in tree is reverted, not landed.

**D5 — Open the app on Stop (`openAppWhenRun = true`; user decision 2026-10-10).**
`StopTimerIntent` sets `openAppWhenRun = true`: tapping Stop opens the app, so the existing reap path (Darwin signal when background-alive, foreground/load sweep otherwise) ends the activity with the Saved card through the unchanged code. Rationale: with D2–D4 dead and push offline-blind, opening the app is the only local, offline-capable mechanism that repaints the activity. The intent keeps its save + signal (the app-open is the delivery guarantee the Darwin post lacked when dead). Cost accepted by the user: the flag is static, so EVERY Island/banner Stop now opens Track — including background-alive stops that previously ended silently. Push rejected (APNs + relay cost, and it degrades to today's orphan whenever offline — the local-first case). Document-only rejected (user call).

OUTCOME (Spike C, 2026-10-10, device): NEGATIVE — technically impossible. The OS rejects the flag at the widget action runner: `LNContextErrorDomain Code=2001 "openAppWhenRun is not supported in extensions"` — the Stop button goes fully dead (no save, no open; four taps device-proven, app dead and background-alive). A `LiveActivityIntent`-conformance variant was not built: the rejection happens in the extension runner before intent-type dispatch, so no protocol changes the gate. Flag reverted. Remaining candidates: documented limitation, Link-based open-and-stop URL (untested — needs its own spike), push (online-only).

**D6 — Link-based open-and-stop for the expanded Island face (Spike D; user decision 2026-10-10).**
The expanded-Isand trailing Stop pill becomes a SwiftUI `Link` to a new stop URL (`lifio://track?stop=1`, shared `LiveActivityDeepLink` contract) instead of `Button(intent:)`: tapping it opens the app, and the app performs the stop itself through the exact in-app path (`reloadTrack()` then `trackVM.stop()` — reload-before-stop orders the cold-open case; no draft → graceful no-op). Rationale: Apple docs ("Launching your app from a Live Activity") list `Link` as a supported deep-link mechanism for the extended presentation, and body-taps already proved the app opens from a dead state on-device. Scope: Island expanded ONLY — lock-screen/banner faces support `widgetURL` but not `Link` per the same docs, so the banner keeps the intent button (today's behavior: saves, orphan ticks until contact). `StopTimerIntent` stays (banner still uses it). Costs (accepted with the direction): every Island Stop opens Track; locked-phone Island Stop unlock-opens instead of stopping silently; the save moves from the intent process to app-on-URL-open. Accepted risk (AI-review round 1): `lifio://track?stop=1` is a state-changing custom-scheme URL invocable by any local caller — nothing distinguishes a genuine Island-pill tap from an externally launched one, and the only gate is `stop()`'s `.running` no-op. Impact is bounded to an early save of the user's own running entry (no data loss, true duration), the same trust the pre-existing `lifio://track` URL already carries — so no caller check was added. Residual window (AI-review round 2, documented not fixed): an Island tap landing while signed out still bumps the counters (`onOpenURL` wraps the root, so it fires behind the auth gate, and the activity survives logout by lock-not-wipe) and replays on the next sign-in's shell mount. Closing it needs producer-side defer-or-drop while signed out, but a `beginSignIn` reset would swallow the Spike-D cold-open replay that `filter { $0 > 0 }` exists for — so the window stays: it needs a signed-out device + a stale live activity + a tap + a later sign-in with an active draft, and its impact is the same bounded early save.

OUTCOME (Spike D, 2026-10-10, iPhone 17 simulator `C18365F5`, device-proven): POSITIVE with two cold-open race fixes. Single expanded-Island Stop tap with the app terminated cold-opens the app (`onOpenURL lifio://track?stop=1 → .stopTimer`, shell observer 0.26s later), saves the entry through the exact in-app path (`Cold fix probe|8m55s|18:46–18:55`), leaves Track idle, and dismisses the activity. Warm Island Stop is single-tap too (`3m44s` entry). Stop link with no active run is a graceful no-op (Track idle, no crash, no phantom entry — History still 3 rows). Race fixes: (a) the `AppShellView` counter observers used `.dropFirst()`, which drops the terminated cold-open bump because it lands before the shell subscribes — first tap only opened the app, second stopped; both observers now use `.filter { $0 > 0 }` (resting 0 filtered, cold-open replay fires). (b) `TrackViewModel.loadIfNeeded()` early-returned while the first appear load was still in flight, so the sequenced `stop()` no-op'd on `.idle` and the late load repainted Running; it now waits for the in-flight load (bounded 500×10ms) before the stale check. No new strings; banner/compact/minimal untouched; TEMP file logging used for the proof removed.

**D7 — Banner open-and-stop (Spike E; user decision 2026-10-11).**
The D6 banner clause ("lock-screen faces support `widgetURL` but not `Link`") was a doc reading, and the 2026-10-11 field report (physical iPhone: banner Stop saves but keeps ticking) made the banner the remaining orphan — so Spike E tests a `Link` Stop on the banner despite the doc's `widgetURL`-only listing. The banner Stop becomes `LiveActivityStopCircleLink` (identical 44pt circle visuals/a11y; intent button kept as the nil-URL fail-safe): label zone keeps its own `widgetURL(trackURL)`, no root-level `widgetURL`, no outer accessibility combine. Rationale: the Island proved `Link`-inside-`widgetURL`-zone wins its taps, and the banner already scopes its label URL the same way.
OUTCOME (Spike E, 2026-10-11, iPhone 17 simulator `C18365F5`, log-proven): POSITIVE on attempt 2. Attempt 1 (sibling `Image.widgetURL(stopURL)`) NEGATIVE — Stop taps delivered `lifio://track`, and removing the outer `.accessibilityElement(children: .combine)` changed nothing (second probe still `lifio://track`): sibling-`widgetURL` loses to the label URL on the banner. Attempt 2 (`Link` wrapping the circle, the Island shape) POSITIVE — single lock-screen Stop tap with the app terminated cold-opens (`lifio://track?stop=1 → .stopTimer`), saves `Banner probe|16m47s|16:11–16:28`, leaves Track Ready, ends the activity (no banner on re-lock). The doc's `widgetURL`-only listing is descriptively wrong for coexistence: `Link` wins where sibling `widgetURL` loses. No new strings; TEMP `TEMP-SPIKE-E-DEBUG` logging removed; `StopTimerIntent` stays (AoD-dimmed/inert fail-safe path + nil-URL fallback).

**D2 — Run-keyed save sidecar file (not suite `UserDefaults`).**
After the existing successful save, the intent writes one tiny file in the App Group container root (sibling of the `active-session-user-id` sidecar): `{ runStartedAt, durationSeconds }`. Rationale: suite-`UserDefaults` reads detach from `cfprefsd` in extension processes (observed on-device — the reason `ActiveAccountFileResolver` is file-first); a plain file is the proven channel. The contract (Codable struct + read/write/delete helpers) lives in `LifioLiveActivityCore` next to `LiveActivitySignal` so app and extension resolve one symbol. This is not a GRDB write, so the LocalStore single-chokepoint invariant is untouched (precedent: `SessionCache`'s session sidecar file). Alternative (suite defaults) rejected by the detach precedent; alternative (new DB table) rejected: the extension must read it while the app is dead, and a sidecar avoids migration/storage-layer coupling.

**D3 — Faces resolve `saved = contentState.saved ?? sidecarMatch(context)`.**
Each face that already branches on `savedDurationSeconds` (banner, expanded leading/trailing/bottom, `islandElapsed` compact trailing) resolves an effective saved value: live content first, else the sidecar when its `runStartedAt` matches `context.state.startedAt` (exact Double round-trip preferred, ≤1s tolerance fallback) — then renders the existing `savedBanner`/saved island text. Rationale: zero new visual language; compact/minimal stay consistent with banner/Island instead of ticking while the banner claims Saved. Fail-closed: missing/unreadable/mismatched sidecar → today's running face (no behavior change, no invented duration — the sidecar carries the same computed duration the intent persisted in the entry). Alternative (new "possibly saved" face) rejected: it would need new strings/locales for a transient state.

**D4 — App-side reap owns cleanup and stays the source of truth for ending.**
`endOrphanedActivities` (via `TimerService`) deletes the sidecar whenever it ends the activity, and end content keeps coming from the entry-recency heuristic — never from the sidecar. Rationale: a sidecar-backed Saved face followed by `end(saved, .after)` shows one continuous Saved card (no double card, no flicker); keying by `startedAt` (unique per run) makes a stale sidecar unable to paint a future run; deletion on reap bounds the file's lifetime. Read errors fail closed to running face (same rule as the draft-read guard).

## Risks / Trade-offs

- [Extension views never re-render post-intent → sidecar unread, face frozen] → Spike B (device): sidecar write + conditional face, kill app, tap Stop, observe. If frozen, Candidate 1 is dead — escalate to push-tokens proposal vs. `openAppWhenRun` spec change vs. documented limitation (decision task, user call).
- [Spike A privilege absent (expected)] → No cost beyond the probe run; D2–D4 proceed.
- [Spike A succeeds] → Drop D2–D4 implementation; narrow the delta spec (save-record requirement goes away, Saved-face scenarios stay) before implementing.
- [Sidecar written but entry save actually failed] → Impossible by construction: write happens only after `.created` + draft-clear success (same guards as the Darwin post today).
- [Keybag-locked sidecar read (reboot before first unlock)] → Fail closed to running face; the intent itself already no-ops gracefully there (no save, no sidecar).
- [Lock-hiding redaction setting] → Unchanged from today; static Saved text redacts exactly like static running text under that setting.
- [Two activities squeeze] → Sidecar face reuses existing faces/frames; no layout change.

## Migration Plan

Spike D landed as the fix (D6 + two cold-open race fixes); Spike E extends it to the banner (D7); D2–D4 and the `openAppWhenRun` flag are reverted, and the TEMP-REPRO `:8081` xcconfig edit is reverted. Rollback = revert the D6+D7 hunks (`LiveActivityDeepLink.stopURL`, `DeepLink.stopTimer`, `AppNavigationStack.islandStopRequestID`, `TimeOfLifeApp.onOpenURL` routing, `AppShellView` observers, widget `LiveActivityStopLink` + `LiveActivityStopCircleLink` + banner scoping, `TrackViewModel.loadIfNeeded` wait) — behavior then identical to `main`.

- Q3: Spike D outcome (Link-based open-and-stop). Resolved POSITIVE by the device run — delta spec rewritten for the Link contract (Island opens-and-stops; banner keeps the intent save path with its known terminated-app limitation).
- Q4: Spike E outcome (banner open-and-stop). Resolved POSITIVE by the device run 2026-10-11 — the banner clause of Q3 is superseded: the banner Stop is a `Link` that opens-and-stops exactly like the Island (sibling-`widgetURL` NEGATIVE, `Link` POSITIVE, both log-proven); the delta spec now contracts banner open-and-stop with no ticking-orphan limitation.
